# 案例研究：一次真实系统的均衡化 A/B 对照测量

> 这是一个用 `lbprobe` 做的完整测量：在同一个 CFD 求解器上，对比**均衡化版本（A）**与**默认分配版本（B）**
> 的性能与进程间等待。数值全部来自实测，环境标识已脱敏。
> 这份文档同时是"怎么读这类报告"的示范 —— 里面有相当一部分结论是**反直觉的**。

## 0. 被测对象

求解器按网格**域（domain）**切分并行计算，一个算例含 3 个域，网格量差别很大（最大域是另外两个的 3 倍和 6.5 倍）。
两版只在"域 → 进程/GPU 怎么分配"上不同：

| | A（均衡化版本） | B（默认分配版本） |
|---|---|---|
| 分配依据 | 按**每个域的网格量**计算，可把一个大域**拆给多个进程** | 按**域个数**轮流分，不看网格量 |
| 进程数 | 4（分配器按负载决定，参数设上限） | 3（等于域个数） |
| 域 → 进程 | 大域 → 2 个进程；另两个域 → 各 1 个 | 三个域 → 各 1 个 |

两版都在**同一台计算节点、同一次调度器资源分配、同一个算例、同样"跑满约 60 秒"预算**下测量。

## 1. 负载分配：A 的单卡峰值得以下降

| 配置 | 每进程负载分布 | 不均衡度 `(max−min)/max` |
|---|---|---|
| **B（默认分配）** | {295 312, 878 080} | **66.4%** |
| **A（本配置，4 进程）** | {295 312, 439 040 ×2} | **32.7%** |
| （参考）A 若用满可用进程 | {295 312, 292 693 ×3} | 0.887% |

实际落到 GPU 上的负载：

| | GPU0 | GPU1 | GPU2 | **单卡最大** |
|---|---|---|---|---|
| A | 439 040 + 134 608 = **573 648** | 439 040 | 295 312 | **573 648** |
| B | 295 312 | 134 608 | **878 080** | **878 080** |

**A 把单卡最大负载压低 34.7%** —— 这是它后面能更快的前提。

## 2. 运行效率：A 更快

六次运行（同机、同资源、同算例、同预算）：

| 版本 | 运行 | 最大迭代 | 吞吐 (次/秒) | 每迭代墙钟 |
|---|---|---|---|---|
| A | ① | 1300 | 21.41 | 46.71 ms |
| A | ② | 1300 | 21.28 | 46.99 ms |
| A | ③ | 1300 | 21.50 | 46.51 ms |
| B | ① | 1100 | 17.98 | 55.63 ms ← 离群 |
| B | ② | 1210 | 20.08 | 49.79 ms |
| B | ③ | 1210 | 20.11 | 49.72 ms |

| 对比项 | A | B | 差异 |
|---|---|---|---|
| 60 秒迭代数 | **1300**（三次完全一致） | **1210**（两次一致） | **A +7.4%** |
| 吞吐 | 21.41 次/秒 | 20.08 次/秒 | **A +6.6%** |
| 每迭代墙钟 | **46.71 ms** | 49.79 ms | **A 快 6.2%** |

> ⚠ **可复现性**：这些数字全部来自同一天、同一台机器、同一次资源分配。节点上的其他负载会影响绝对值，
> **不能当成"以后每次都是这样"**。可信的是**同一会话内的相对关系**（A 三次迭代数完全一致，B 两次一致）。
> 跨环境比较前必须重新标定。

## 3. 等待：这一节的结论和第 2 节方向相反

### 3.1 总量与分段

| 指标（rank·ms） | A（4 进程，1300 迭代） | B（3 进程，1210 迭代） |
|---|---|---|
| 集合通信相互等待 · 合计 | 7208.74 | 3115.52 |
| ├ 启动段（前 5 s） | 6519.49 | 3115.52 |
| └ **稳态段** | **689.24** | **0.00** |
| 点对点等待 · 合计 | 1241.63 | 11.26 |
| └ **稳态段** | **203.44** | **10.12** |
| **稳态合计** | **892.68** | **10.12** |

> 为什么必须分段：两版的等待都 90% 以上压在开头 2~3 秒的同几处世界归约上（读网格、划分、应用均衡化计划），
> 那是**一次性成本**。不分段就等于拿"启动开销"比稳态性能。

### 3.2 每迭代归一化

| 指标（rank·ms/迭代） | A | B |
|---|---|---|
| 集合通信相互等待（稳态） | 0.5302 | 0.0000 |
| 点对点等待（稳态） | 0.1565 | 0.0084 |
| **稳态合计** | **0.687** | **0.0084** |

### 3.3 点对点：A 的调用次数是 B 的 83 倍，但每次都很便宜

| | A | B |
|---|---|---|
| `MPI_Wait` 调用次数 | **201 182** | **2 420** |
| 平均每次阻塞 | 0.0011 ms | 0.0045 ms |
| 单次最长阻塞 | 512.41 ms（启动段） | 0.17 ms |

A 的点对点流量主要来自"大域被拆成两半后，那两个进程之间的内部边界交换"（近 20 万次、只涉及 2 个进程）。
这 20 万次交换合计只花 196 rank·ms，**平均每次 0.001 ms** —— 均衡化引入的这条并行代价通道非常便宜。

## 4. 为什么 B 的等待明显更少（四个原因，按重要性排序）

**① B 根本没有跨进程归约通道（结构性原因，最主要）。**
B 里每个网格域整体归属一个进程，因此各进程所在的**分组通信子只有自己一个成员**。
`gsum/gmax/gmin` 这类分组归约（每进程约 5 984 次）**全部退化为本地空操作**，不产生任何跨进程同步，
自然不存在"到齐前等待"。分析器把这些按"单进程同步点"过滤后，B 整场只剩 74 个真实的跨进程同步点。
而 A 把大域拆成两半后，那两个进程共享同一个分组通信子（约 7 000 次），**每一次都是真实的跨进程同步**，
累加出 A 稳态的 689.24 rank·ms（约 0.098 ms/次）。

**② B 的跨进程交换量小一个数量级。** 要同步的点少，能等待的机会就少。

**③ 两边单次交换几乎都不阻塞，"总量差"来自次数而不是单次时长。** 这说明这套代码的界面交换本身很便宜。

**④ 这个算例的每迭代耗时以固定开销为主，网格量差异没有等比转成时间差。**
假如每迭代耗时与网格量成正比，B 里最大域那个进程会比最小域那个慢 6.5 倍，另外两个进程每步都得等它，
应当出现巨量等待；但实测 B 的稳态集合通信等待为 **0.00**。旁证：A 把单卡最大负载压低 34.7%，
每迭代只快了 6.2% —— 若纯计算密集，本应快约 1.53 倍。

> **一句话：B 等待少，是因为它没有把负载摊开。"不分享工作"自然"不用等"——
> 这不是分配更优，而是同一件事的另一面，也正好解释了 B 为什么算得慢。**

## 5. 代价与收益

| 项 | 数值 | 说明 |
|---|---|---|
| A 每迭代省下的墙钟 | **3.28 ms**（49.79 → 46.51） | 来自单卡负载下降 34.7% |
| A 每迭代多付的等待 | **0.687 rank·ms**（≈ 每进程 0.172 ms） | 来自拆域后的边界同步 |
| **收益 / 代价** | **≈ 19 : 1** | 等待开销占每迭代时间的 **0.37%** |
| 60 秒内多完成的迭代 | +90 次（+7.4%） | 1300 vs 1210 |
| 启动一次性代价 | A 比 B 多 ≈ 4 441 rank·ms | 应用均衡化计划并重分配网格，不进稳态 |

| 检查 | A | B |
|---|---|---|
| 事件文件完整 | 4 / 4 | 3 / 3 |
| 非法日志行 | 0 | 0 |
| 被采集上限截断 | 否 | 否 |

## 7. 边界与未覆盖

1. **只覆盖 MPI 层**：集合通信与点对点的 `MPI_Wait`。GPU 核内等待（核函数排队、显存同步）不经过 MPI，探针看不到。
2. **单节点、单次会话**：未做跨节点测量；节点其他负载未控制，绝对值不可跨会话比较。
3. **B 的重复次数不足**（2 次、相差 10%），"+7.4%"应视为待复核；A 侧三次一致，可信度更高。
4. **A 还有余量没用**：本次参数只给了 4 个进程（不均衡度 32.7%）；分配器自选更多进程时可做到 0.887%（未实跑，属参考值）。
5. **A 的进程数多于 GPU 数**：4 个进程挤 3 块 GPU，需确认显存/带宽没有成为新瓶颈。

## 8. 这次测量教给我们的三件事

1. **不能拿"等待总量"给两个版本排名。** 那是拿"不并行"和"并行"比谁不用等。
   要先问"它的跨进程同步点有多少个"，再问"每个同步点等了多久"。
2. **必须分段。** 启动阶段的一次性同步（读网格、划分、应用均衡化计划）能占全部等待的 90%，
   混在一起就会得出"均衡化很慢"的错误结论。
3. **归因必须按等待量加权。** 本次 A 的最忙同步点上，最后到达者只占该同步点的 40% 次数，
   但按等待量算是绝对主导 —— 按次数统计会把真实瓶颈稀释掉。
