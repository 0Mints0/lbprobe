# 样例报告

四个合成算例的完整输出，用来**演示口径**，不是任何真实程序的结论。
全部由本仓库的仿真后端生成（不需要 MPI），生成方式：

```sh
make && make sim-all
```

每个算例两个文件：`*-report.md`（给人看的中文报告）、`*-analysis.json`（机器可读）。

| 算例 | 负载形态 | 判定 | 这张报告想说明什么 |
|---|---|---|---|
| [01-imbalanced-load](01-imbalanced-load-report.md) | 各进程负载不均 | 存在相互等待 | 最典型的情形：进度不一致，等待分散在多个进程之间 |
| [02-uniform-load](02-uniform-load-report.md) | 负载均匀 | 有等待，但主要不是进程间等待 | **对照组**：负载均匀时相互等待大幅下降，说明判定不会把计时抖动当成失衡 |
| [03-single-rank-lagging](03-single-rank-lagging-report.md) | 一个 rank 有长设备同步 | **单向等待**，99% 归因 rank 7 | 责任归属：不是"大家在互相等"，而是"大家在等它一个" |
| [04-empty-rank](04-empty-rank-report.md) | 一个 rank 没有分区 | 存在相互等待 | 空分区并没有让它先到，说明瓶颈不在负载分配本身 |

## 为什么第 3 张报告最重要

它演示了本工具最容易做错的判断：

> rank 7 只在 **41%** 的同步点上最后到达 —— 按**次数**看像是"等待很分散"，
> 但那几次每次携带 2.6 秒的到达离散，按**等待量**算占 **99%**。

这就是报告坚持"归因必须按等待量加权，不能按次数"的原因。
按次数统计会被大量几乎不耗时的同步点稀释掉真实瓶颈。

## 各报告的数据可靠性

每份报告第 5 节都自检了数据完整性：非法日志行 0、无未正常收尾的 rank、
无未配对的 enter、各 rank 调用次数一致。同时自检了拆分恒等式
`到齐前等待 + 到齐后耗时 = 等待时长`（报告中两者之和与实际等待时长的偏差 < 0.01 rank·ms）。
