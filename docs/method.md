# 测量方法与判定口径

**版本** v2.0 · **产出物** 一份测量报告（`report.md` + `analysis.json`）

本版只回答两个问题，不做别的：

1. 当前计算过程中，进程之间**是否存在相互等待**？
2. **等待时间是多少**？

---

## 0. 范围（明确不做什么）

| 不做 | 原因 |
|---|---|
| 不做均衡化开/关对照 | 只测当前均衡化后的结果，不需要参照组 |
| 不判断"均衡化是否拖慢" | 同上 |
| 不做故障注入、不做死锁判定 | 已确认最坏情况是变慢，不是卡住 |
| 不给解决方案、不改你的代码 | 只要测量报告 |
| 不测失衡度、不采集负载数据 | 与"是否有相互等待"无关，且会增加插桩量 |

---

## 1. 测量定义

同步点上的一段可计时的时间。每次同步（`barrier`/`Allreduce`/`Alltoallv`/`Sendrecv`…）里：

- `in_r`、`out_r`：rank *r* 进入/退出该集合通信的时刻（探针打点）；
- `in_last = max(in_r)`：最后一个到齐的进程的时刻。

| 分段 | 定义 | 含义 |
|---|---|---|
| **到齐前等待** | `in_last − in_r` | 我算完了在等人。**没有任何通信在为我服务，这就是"等待"** |
| **到齐后耗时** | `out_r − in_last` | 全组到齐后原语自身的开销，不计入等待 |

两者之和**严格等于**该 rank 这次的等待时长，所以拆分不重不漏（报告里会自检这一恒等式）。

聚合量：

| 量 | 含义 |
|---|---|
| **相互等待时长** | `Σ(各 rank 的到齐前等待)`，单位 rank·ms（再换算成核·秒） |
| **平均同时在等待的 rank 数** | 等待区间并集的时间加权平均，即"平均有多少个进程在干等" |
| **等待热点** | 按同步类型（barrier/allreduce/alltoallv…）分解，指向具体的通信点 |
| **等待责任归属** | 每次同步里谁最后到达；再按**等待量加权**统计这份等待该归给谁 |

### 1.1 判定：相互等待 vs 单向等待

"有等待"和"相互等待"不是一回事。只看集合通信的进入/退出时刻也能区分：

| 形态 | 判据 | 含义 |
|---|---|---|
| **相互等待** | 等待**分散**在多个进程之间（最集中的那个进程占不到 60%） | 谁也不固定落后，是进度整体不一致 → 互相等待 |
| **单向等待** | 某一份等待**几乎全归因于一个进程**（≥ 60%） | 其余进程在等它一个 → 单点落后（负载不均或设备/IO 阻塞） |
| 原语开销主导 | 到齐前等待占全部等待 < 50% | 等待来自集合通信本身，不是进程间等待 |
| 无实际影响 | 平均同时在等待的 rank 占比 < 5% | 等待量级可忽略 |

> **归因必须按等待量加权，不能按次数。** 实测中曾出现：末位 rank 只在 42% 的同步点上最后到达，看起来"分散"，但它那几次每次携带 2.5 秒的到达离散，按等待量算占 **99%** —— 显然是单向等待。按次数统计会被大量近乎不耗时的同步点稀释掉。

## 2. 插桩：最小集（每个集合通信前后各一行）

### 2.1 插入方式

```c
#include "lbprobe.h"

int main(int argc, char **argv) {
    MPI_Init(&argc, &argv);
    lb_init();                       /* 1. 启动时一次 */
    ...
    for (iter = 0; ...; iter++) {
        /* 计算部分不动 */

        /* 2. 均衡化里的每个集合通信, 前后各一行 —— 这就是全部插桩量 */
        lb_wait_begin(LB_ALLREDUCE, 100);
        MPI_Allreduce(&local_load, &max_load, 1, MPI_DOUBLE, MPI_MAX, MPI_COMM_WORLD);
        lb_wait_end(LB_ALLREDUCE, 100, 1);

        ...
        lb_wait_begin(LB_ALLTOALLV, 101);
        MPI_Alltoallv(...);
        lb_wait_end(LB_ALLTOALLV, 101, 1);
    }
    lb_finalize();                   /* 3. 退出前一次 */
    MPI_Finalize();
}
```

也可以直接用包装函数替换调用（同样带插桩）：

```c
double mx = lb_allreduce_max(100, local_load);
int    ok = lb_alltoallv(101, sendcnt, recvcnt);
lb_barrier(102);
```

**要点**：`tag` 用你代码里本来就有或自编的整数即可，同一个调用点用同一个 tag。手工插两行的方式对任何 MPI 调用都适用（包括 `Bcast`、`Iallreduce+Wait`、`Sendrecv`），不受包装函数覆盖范围限制。

### 2.2 编译与开关

```sh
mpicc -DLBPROBE_HAVE_MPI -Iinclude your_source.c src/lbprobe.c -o your_app
```

| 宏/环境变量 | 作用 |
|---|---|
| `-DLBPROBE_HAVE_MPI` | 走真 MPI；不加则走仿真后端（仅本机验证用） |
| `-DLBPROBE_OFF` | 全部接口退化为空操作，**零开销**（可用于正式生产构建） |
| `LB_RUN_DIR` | 事件日志目录。**必须放节点本地盘**（`/dev/shm` 或 `$TMPDIR`） |
| `LB_COLLECT_DIR` | 可选。收尾时把日志汇集到共享目录，供离线分析 |

运行时还可用 `lb_enable(0/1)` 只测量中间某一段（例如只关心均衡化触发的那几轮），别的阶段零开销。

### 2.3 插桩开销

每个集合通信点 2 次时钟读取 + 1 行文本日志；无线程、无锁、无对端文件、无轮询。
建议正式测量前先跑一次 `-DLBPROBE_OFF` 与开启状态的对照，标定探针自身开销（目标 < 1%）。

### 2.4 需要交付的文件

| 文件 | 说明 |
|---|---|
| `include/lbprobe.h` + `src/lbprobe.c` | 常规两文件布局（130 + 326 行） |
| `lbprobe_single.h` | **单文件版**（头+实现合并，490 行）：放进一个文件，在一个编译单元里定义 `LBPROBE_IMPLEMENTATION` 即可 |
| `tools/lb_analyze.py` | 离线分析，生成报告（仅用 Python 标准库） |

两种布局二选一，不要同时用。`lbprobe_single.h` 不入库，用 `python3 tools/make_single.py` 生成；
详细步骤见 [`usage.md`](usage.md)。

只有一个后台动作：每个 rank 写自己的一个文本日志文件。其余全部是离线分析。

## 3. 输出：测量报告

`tools/lb_analyze.py <运行目录>` 生成 `report.md`（中文）与 `analysis.json`（机器可读）：

```
0. 结论            是否存在相互等待/单向等待 + 等待时间 + 判定阈值
   关键量表        相互等待时长、同步等待合计、到齐前/到齐后占比、
                   平均同时在等待的 rank 数、等待占比、最大到达离散度
1. 等待热点        按同步类型（barrier / allreduce / alltoallv …）分解
2. 等待责任归属    每次同步的最后到达者 + 该 rank 自身等待占比
3. 逐同步点明细    每个同步点的到达离散、到齐前等待、到齐后耗时、最后到达者
4. 各 rank 等待分布 每个 rank 的等待时长及其占自身墙钟比例
5. 数据可靠性      非法日志行、未正常收尾、未配对的进入、调用次数不一致
```

## 4. 实测样例（仿真后端，8 进程，用于说明口径）

| 算例 | 判定 | 相互等待 (rank·ms) | 平均在等 (rank) | 等待热点 |
|---|---|---|---|---|
| 失衡负载 | **存在相互等待** | 8709.8 | 5.48 / 8 | allreduce 87.5% |
| 均匀负载 | 存在等待，但主要非进程间等待 | 856.4 | 4.05 / 8 | — |
| 末位 rank 长设备同步 | **单向等待**（归因 rank 7，占 99%） | 141600.5 | 6.82 / 8 | allreduce 97.8% |
| 末位 rank 无分区 | **存在相互等待** | 7834.0 | 5.60 / 8 | allreduce 85.2% |

第二行与第一行的对比说明口径有效：负载均匀时相互等待从 8709.8 降到 856.4（约 1/10），
说明判定不会把计时抖动当成失衡。第三行说明单向等待能被正确识别出来、并把责任归到具体进程，
而不是笼统地报"有等待"。

样例报告：[`samples/`](samples/)（完整 `report.md` 与 `analysis.json`）。
**这些是合成负载下的口径演示，不是真实程序的结论**；真实案例见 [`case-study.md`](case-study.md)。
仿真后端用的是真实时钟，同一算例两次运行的绝对数值会有几 % 波动，判定结论稳定。

管线自检（对象是测量链路本身，非被测代码）在本机 10/10 通过，含：
- 拆分恒等式 `到齐前等待 + 到齐后耗时 = 等待时长`；
- 日志完整性（非法行 / 未收尾 / 未配对进入）；
- 单向等待的归因正确性；
- 均匀负载下相互等待显著下降（口径不会把 jitter 当成失衡）。

## 5. 集群执行注意事项

1. **事件目录放节点本地盘**：逐事件写盘若落在 Lustre/GPFS/NFS 家目录上会拖慢并行文件系统，反过来干扰测量。用 `LB_RUN_DIR=/dev/shm/...`，并设 `LB_COLLECT_DIR` 指向共享目录，探针在 `lb_finalize()` 时一次性汇集。
2. **`timeout` 兜底**：即使预期不会卡住，也用 `timeout -k 5 <秒> mpirun ...` 包一层，否则一旦异常，作业会占着机时直到墙钟上限。
3. **采样时长**：覆盖若干个完整迭代；建议对关键算例重复 3 次取中位数（MPI 计时抖动不可忽略）。
4. **跨节点对时**：跨节点比较绝对时刻依赖 NTP/PTP。对时不可靠时，跨节点只看聚合量（等待时长、热点），别看单点的绝对到达时刻。
5. **规模相关的观察点**：进程数增大时，`Allreduce` 的等待会随参与数增长；同一算例在 2~3 个规模上各测一次，可以看出等待是否随规模放大。

## 7. 接入前值得先确认的几点

1. **均衡化涉及的集合通信调用点**：文件与函数位置（决定在哪插那两行）；
2. **`tag` 规划**：同一调用点用同一 tag 即可；
3. **均衡化的开关方式**（若还想区分"均衡化相关"与"其它"同步点的等待，可用不同的 `kind` 值或 tag 段）；
4. **算例信息**：典型进程数、迭代数、单迭代耗时（决定采样时长与重复次数）；
5. **报告受众**：`report.md` 是直接交给他人，还是要并入正式的性能测试报告（影响详略）；
6. **确认阈值**：§1.1 的三个阈值（5% / 50% / 60%）是否符合你的判断口径。
